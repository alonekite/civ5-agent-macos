# ADR-0017: Separate bridge-session identity from match identity

Status: Accepted

Date: 2026-09-16

## Context

M5 needs to keep records from different matches separate, while M6 must reject
a plan aimed at a different live game connection. Earlier drafts called both
needs “game identity.” The implemented live-state schemas expose turn and active
player, but no target-verified identifier that remains stable across saving,
loading, reconnecting, and restarting Civ V.

Inventing such an identifier from mutable state would create false safety. Letting
M5 assign the identifier used by M6 would also recreate the execution-to-journal
dependency rejected by ADR-0016.

## Decision

Use two deliberately different identities:

- `bridge_session_id` is a canonical UUIDv4 generated by the connection-owning
  bridge after a live connection and `InGame` Lua state have been selected. It
  remains fixed only for that connection-owner lifetime. It changes on watcher
  restart, reconnect, or Lua-state reselection and does not claim to identify a
  saved match across sessions.
- `match_id` is a canonical UUIDv4 explicitly created when an M5 journal is
  created. It remains fixed for that journal and identifies the historical
  record, not a fact asserted by Civ V.
- Every captured live observation and command lifecycle recorded by M5 carries
  the current `bridge_session_id`. The journal header carries `match_id`.
- A journal may bind a later bridge session only through an explicit,
  append-only `session_binding` record. Until a stable match fingerprint is
  derived from target-verified Civ V APIs, automatic cross-session binding is
  prohibited. Ambiguity starts a new journal or requires explicit operator
  confirmation.
- M6 targets `bridge_session_id`, turn, active player, and a live-state basis.
  It does not use `match_id` and does not query M5. A plan becomes stale after a
  reconnect even if the user loaded the same save.
- Existing live-state schemas 2–5 do not provide `bridge_session_id`. A shared
  observation/command envelope extension must be implemented and tested before
  M5 or M6 claims identity isolation.

The exact public envelope name remains pre-stable until M7, but these meanings
and the prohibition on automatic cross-session inference are normative.

## Consequences

- M5 and M6 can share bridge-owned session metadata without depending on each
  other.
- Initial M6 plans are intentionally short-lived and fail closed after bridge
  restart or reconnect.
- Long-running match history can span sessions only when the binding decision is
  explicit and auditable.
- Future target-machine evidence may support a stable match fingerprint. Adding
  it requires a new contract version and bounded live verification; it must not
  silently change the meaning of either UUID.
- Storage fallback readers also need an explicit capture-session identity rather
  than inferring one from mutable snapshot fields.

## Alternatives considered

- Hash turn, player, civilization, and visible state: rejected because different
  matches can collide and ordinary gameplay changes the input.
- Let the journal's `match_id` authorize execution: rejected because M6 must
  operate without M5 and journal history is not live proof.
- Reuse one UUID across reconnects automatically: rejected because the current
  bridge cannot prove that Civ V still has the same save loaded.
- Omit identity until M7: rejected because both M5 isolation and M6 stale-plan
  rejection depend on its semantics now.

## Supersedes

This ADR replaces uses of the ambiguous term “game identity” in the proposed M5
and M6 contracts. It does not change ADR-0016's separation between journal and
execution state.
