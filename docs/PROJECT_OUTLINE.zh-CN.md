# Civ5 Agent 项目大纲

本文是项目的中文认知入口，用于快速、反复理解项目目标、模块边界、数据流和开发顺序。它只总结当前有效设计；详细规范由链接中的英文文档维护。

## 一、项目要解决什么问题

目标是在 Apple Silicon macOS 上，为原版 Civilization V 建立一个可复用、可测试、安全的读写核心：

```text
Civilization V Lua ↔ Python
```

图中的 knowledge 只供未来计划生产者使用，不直接输入执行器。执行器仅依赖
bridge 的实时状态、会话身份和动作契约。

这个核心必须能够：

1. 从正在进行的对局读取结构化状态；
2. 让 Python 提交严格白名单内的游戏动作；
3. 在执行动作前检查游戏条件；
4. 执行后重新读取状态，证明动作确实成功；
5. 提供版本化规则知识，供未来战略、战术和 vertical skills 查询，并在核心确有需要时校验稳定标识。

当前仓库不开发 LLM 决策、working memory、strategic memory 或 MCP。它们属于未来独立的上层系统。

## 二、核心安全原则

- 不假定 Windows DLL 能在 macOS 使用。
- 不假定 Civ V Lua 可以自由访问文件、网络或操作系统。
- 未在目标机器验证的 IPC 机制一律视为未知。
- 只开放明确列出的动作，不开放任意 Lua 执行。
- 每次写入都必须保存写前状态、执行动作、再读取写后状态。
- 实机实验必须可复现，并记录环境、步骤、证据和恢复结果。
- 不收集或发布领袖 AI flavor、性格、行为权重。
- 固定知识来自用户本地安装的游戏数据，不把模型生成内容当作事实。

## 三、当前系统结构

```text
Civilization V
      ↕
bridge：FireTuner / 后备存储、状态读取、白名单动作、写后验证
      ├──────────────→ turn journal（计划中：已捕获事实档案）
      │
      └→ live state ─────────────┐
                                 ▼
knowledge ─────────────→ 上层战略、战术与 skills（未来项目）
                                 │
                                 ▼
                           明确 TurnPlan
                                 │
                                 ▼
                      deterministic turn executor
                                 │
                                 ▼
                       bridge 执行并回读验证
```

### bridge

负责与游戏通信、解析实时状态、验证动作参数、执行白名单动作，并通过回读判断成功或失败。当前实机验证的传输是游戏内置 FireTuner；watcher 独占连接，再通过私有 Unix socket 为命令行提供串行访问。

详见：[bridge 模块](modules/bridge.md)。

### knowledge

保存与某一局存档无关、但与规则集版本有关的固定事实，例如科技、政策、单位、晋升、文明、宗教、建筑、资源和地形。数据包含稳定游戏 ID、数值、前置条件、替换关系和来源哈希。

基础知识不可被某局游戏修改。M4 只根据明确的游戏速度、难度、文明、政策和信条等条件提供结构化知识视图；有效数值、候选比较和路线分析以后由战略、战术及 vertical skills 按实际需求处理。

详见：[knowledge 模块](modules/knowledge.md) 和 [知识契约](KNOWLEDGE.md)。

### turn journal

计划中的事实档案模块。它会逐条追加记录期间实际捕获并验证、且属于当前
schema 支持范围的回合快照、命令、执行结果、写前/写后状态和验证错误，用于
审计、复现、调试和离线分析。它不声称记录断线期间、隐藏状态或 schema 之外
的事实。

它不总结历史、不推断对手意图、不设定战略，也不把整局记录直接交给执行器。

详见：[journal 模块](modules/journal.md)。

### deterministic turn executor

接收人工或未来战术层给出的明确 `TurnPlan`，检查目标对局、回合、玩家和状态前置条件，依次调用白名单动作，并在每一步后回读验证。它可以报告“尚需选择科研”等事实要求，但不能替上层选择科技、生产项目、移动目标或战略。

当前 Python 包仍名为 `controller`，只保留早期回合就绪检查和显式结束回合的 MVP 证明；M7 再稳定公共名称。

详见：[controller 模块](modules/controller.md)。

### session identity 与 match identity

当前已验证的 Civ V 接口没有能够跨存档、读档和重连保持稳定的永久对局 ID。
因此 bridge 为每个连接周期创建 `bridge_session_id`，供 M6 防止计划跨连接误
执行；M5 在新建 journal 时创建独立 `match_id`。后续连接只有通过明确、追加式
绑定才能写入同一 journal，当前禁止根据可变快照自动推断“仍是同一局”。

### CLI

CLI 是模块外的一层薄入口，提供状态监听、命令提交、安全预检、知识导入和旧 controller/M6 执行器入口。业务规则不应只存在于 CLI 中。

详见：[CLI 模块](modules/cli.md)。

## 四、已经完成什么

- 已识别目标机器、游戏版本、数据目录和 Lua 环境。
- 已证明 Python 能从真实对局读取回合、玩家、经济、城市、科研和单位状态。
- 已证明 `end_turn` 能推进回合并通过回读验证。
- 已实机验证选择科技和设置城市生产。
- 已实现 watcher 单连接所有权、私有本地 IPC、命令审计、重复命令抑制和安全预检。
- 已离线实现 bridge-session envelope：每个连接周期获得 UUIDv4，读取会返回它，
  写入必须回送同一身份，缺失或过期身份会在动作执行前被拒绝。
- 已建立版本化知识核心，并导入时代、科技、单位、单位类别、升级、晋升、政策、政策树、建筑、奇观、资源及现有关系。
- 已建立基础回合就绪检查和显式结束回合的 MVP 证明。

实时完成情况以 [PROJECT_STATE.md](PROJECT_STATE.md) 为准；验证证据以 [EXPERIMENT_LOG.md](EXPERIMENT_LOG.md) 为准。

## 五、接下来按什么顺序开发

### M3：完成规则集知识覆盖（已完成）

1. 文明、领袖、特性和独特替换（已完成离线实现与真实数据库验证）；
2. 宗教、信条、伟人和专家（已完成核心离线导入）；
3. 地形、地貌、改良设施、道路、建造动作和产出（核心实体和直接关系已完成）；
4. 带数值的产出关系、项目、生产过程以及政策、建筑、资源效果关系（已完成）；
5. 胜利、游戏速度、难度、地图大小及其他全局规则（已完成）。

### M4：规则集知识视图（已完成）

在不修改基础知识的前提下，校验某局明确声明的 DLC/Mod、文明、政策、信条、速度、难度和地图大小，并提供带来源的结构查询。当前只解析单位/建筑类别的默认项、文明替换或禁用状态，不进行数值推演、候选评分或行动选择。

### M5：事实型 turn journal

schema 1 追加式 codec 和私有 JSONL store 已离线实现：包含 `match_id`、明确的
session binding、连续序号、SHA-256 链、文件锁、`fsync`、记录大小限制和损坏/
截断拒绝。显式启用时，watcher 已能记录变化后的验证快照和带回合依据的内存命令
结果；`new` 新建 journal，`resume` 才会绑定新 session，重连不会自动续接。它为
未来战术/战略层的历史选择、复盘、比较、调试和审计保存事实，不是 M6 的执行
状态。现有 M2 command audit 是独立安全记录；M5 只通过 command UUID 关联，
不解析 audit 文件。确定性校验、按追加顺序回放和脱敏结构导出已离线实现；导出
不含 payload、时间戳、对局/会话身份、哈希或源路径，但回合与事件时间线仍可能
敏感。M5 离线实现已完成，尚待一次受控实机验证。

### M6：确定性回合执行器（依赖 M2，与 M5 独立）

定义版本化 `TurnPlan`，只执行其中明确列出的白名单动作；每一步回读验证，状态
漂移、缺少决定或恢复不明确时暂停，不自行重新规划。完整回合计划的
`end_turn` 必须是明确的最后一个动作，验证成功后才能返回 `completed`。M6 可
发布事实事件，由 watcher/CLI 组合层选择写入 M5；M5 不控制执行，记录失败也
不能触发游戏动作重试。schema 1 的计划/动作/报告模型、初始完整状态摘要和严格
准入校验已离线实现。M6 不查询 knowledge；规则知识由计划生产者使用。当前进程
内执行核心也已实现逐步重读、前后状态连续性、要求缺失暂停、漂移拒绝和未知结果
不重试；watcher/CLI 适配、事实事件与明确恢复仍待实现。

### M7：稳定公共 API

稳定状态读取、白名单动作、知识查询、journal 查询、TurnPlan 和执行报告接口及其兼容策略。

### M8：1.0 发布准备

完成必要的实机验证、安全复查、安装说明、迁移说明和版本化发布。

详细验收条件见：[MILESTONES.md](planning/MILESTONES.md)。

## 六、未来决策与 LLM 系统放在哪里

未来另建上层项目或独立包，统一设计：

- context builder；
- working memory；
- strategic memory；
- LLM adapter；
- 候选决策和评估；
- 科研、军事、探索、城市发展等 vertical skills 及其确定性规则。

有效数值合成、反事实比较、路线分析和后果评估由这些战略、战术及
vertical skills 按实际需求实现，不放入当前回合执行层。当前核心中的
M4 只提供结构化知识视图。

working memory 会选择近期重要变化、对手已观测信息和近期意图；strategic memory 会维护获胜目标、科技/政策路线和扩张、外交、军事方向。它们与提示词、上下文预算、摘要、推断、过期和计划修订密切相关，因此不嵌入当前核心。

未来 LLM 只能通过公共接口读取状态、知识和 journal，并提交候选意图。最终动作仍必须经过当前核心的白名单、合法性检查和写后回读。

## 七、如何判断一项能力真的完成

```text
设计边界明确
    ↓
实现及离线测试通过
    ↓
敏感信息与禁止字段扫描
    ↓
CI 通过
    ↓
需要时在目标 Mac 进行受限实机实验
    ↓
实验日志记录证据和恢复状态
    ↓
更新项目状态、测试矩阵和里程碑
```

“代码存在”“离线测试通过”“检查了游戏自带 Lua”“实机验证成功”是四种不同证据，文档中不能混用。
